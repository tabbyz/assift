## 1. 目的と完了条件

サイトに `support@assift.com` を載せるのをやめ、問い合わせの入口を**フォーム**に絞る。フォームはメールで `support@` に届け、受信箱（032 で入れる Missive。入れる前は Gmail）で返す。

狙いは 2 つ。迷惑メールを増やさないこと（新しく集められるのを防ぐ。もう出回っている分は減らない。§3-1）と、問い合わせに要る情報（誰の・どの店舗の・エラー番号・画面のスクリーンショット）を最初から揃えること。

- [ ] `/contact` から送ると `support@` に 1 通届き、受信箱から返すと**相手のアドレスに**届く（Reply-To。§4.5。Missive での振る舞いは 032 §4-1 で確かめる）
- [ ] ログイン中に送ると、アカウント・店舗・エラー番号が本文の区切り線のあとに自動で付く（§4.4）
- [ ] 画像を 3 枚まで添付でき、サーバーで書き出し直した JPEG としてメールに付く（§4.7）
- [ ] BotID・回数の制限・ハニーポットが掛かっている（§4.6）
- [ ] サイトの `mailto:` が、§4.8 の表のとおりフォームへのリンクに置き換わっている（残すのは表のとおり）
- [ ] CSP（022）を変えずに動く（外部のスクリプト・iframe を足さない。BotID は同一オリジン。§4.6）
- [ ] プライバシーポリシー（お問い合わせの内容に自動で付く情報と添付）が実装と食い違わない（§6。Missive の行は 032）
- [ ] `lint` / `typecheck` / `test` が通る（スキーマは触らないので `supabase test db` は変化なし）

- **受信箱（Missive）の設定と、ポリシーの Missive の行**: 032（10/25〜10/26）

- **受け付けの自動返信メール**: 未ログインのフォームから任意のアドレスへメールを送れる口になる（§3-7）
- **送信までの時間のチェック**: ボットは待ち時間をランダムに入れられ、自動入力で素早く送る人を誤って弾く（§3-11）
- **Cloudflare Turnstile・reCAPTCHA**: BotID で足りる見込み。BotID が CSP と合わないときだけ Turnstile と比べ直す（§4.6）
- **`info@assift.com` の廃止**: v1 からの問い合わせを受けるため残す（016-terms §7 のまま）

## 3. 決定（案。2026-10-19）

| # | 項目 | 案 | 理由 |
| --- | --- | --- | --- |
| 1 | アドレスを載せる場所 | **特商法の表記と global-error だけに残す**。ほかはフォームへのリンク（§4.8） | アドレスは規約・ポリシー・030 の告知・Stripe の公開情報で既に出回っており、消しても届く迷惑メールは減らない。新しく集められるのを減らすのが目的。特商法の表記は法令の確認まで残す（§9-1）。global-error はアプリが落ちたとき（フォームも動かない）にしか描かれず、クローラーが読まない |
| 2 | 受信箱 | `support@`（Google Workspace）。Missive は 032 で入れる | フォームは受信箱に依らない（§3-3） |
| 3 | フォームから受信箱への渡し方 | **メール**（Resend で `support@assift.com` へ送る）。Missive の API は使わない | 受信箱の SaaS を替えても転送先を変えるだけで済む。032 の前でも後でも同じ実装で届く。Missive の API は Productive 以上で、縛られる |
| 4 | ページ | **`/contact` の 1 つ**（`(public)/(site)/contact`）。ログインの有無で中身を変える | 入口が 1 つなら案内が簡単。(site) のヘッダーはログイン中なら右上を「アプリを開く」（`/tenants`）に替える（規約・ポリシー・特商法の表記も同じ。§10.5） |
| 5 | ログイン中の返信先 | アカウントのメールアドレスを使い、入力させない | 本人確認が済んだアドレスにしか返さない。打ち間違いが無い |
| 6 | 保存 | DB に保存しない。送信の失敗は画面に返す | §2。やり直しで二重に届かないよう `Idempotency-Key` を付ける（§4.5） |
| 7 | 自動返信 | **送らない**。完了の画面に「ご入力のアドレスへ返信します」と書く | 未ログインのフォームに他人のアドレスを入れると、私たちから他人へメールを送れてしまう（踏み台）。バウンス・迷惑メールの報告が増えると Resend が送信を止め、**認証メールまで止まる**（030 §6.3） |
| 8 | メールの形式 | **テキストだけ**（HTML を作らない） | 自分の受信箱に送るだけで、見た目は要らない。利用者の入力を HTML に埋め込まないので、エスケープの漏れが起きない |
| 9 | 自動で付ける情報 | ユーザー id・メールアドレス・店舗（id と名前。RLS で見えるものだけ）・エラー番号・ブラウザ（User-Agent）。**押す前に開いていた画面（`?from=`）は付けない** | 「どの店舗の話か」が聞き返しの理由で一番多い。エラー番号はログを探すのに直接使える。メニューはどの画面にもあり、押した画面と困っている画面が同じとは限らないので、開いていた画面は検証の手間のわりに役に立たない（要るなら本文に書いてもらう）。契約の状態はユーザー id から管理画面（020）で引けるので本文に入れない。Stripe の id など、本人に見せない値は入れない（返信の引用で相手に戻りうる。§4.4） |
| 10 | 環境 | 送るのは `RESEND_API_KEY` と `CONTACT_INBOX` があるときだけ。開発で無ければコンソールに出して成功にする | プレビューから本番の受信箱に届かないようにする（§4.9） |
| 11 | 迷惑な投稿の対策 | **Vercel BotID**（見えない判定）+ **Vercel Firewall の回数の制限** + **ハニーポット**。時間のチェックはしない | ハニーポットと時間のチェックだけで守るのは古い。ブラウザを丸ごと動かすボットは見えない欄も待ち時間も避ける。今の主流は見えない判定と回数の制限の重ね掛け。BotID は自分のドメインから判定のスクリプトを配るので CSP を変えずに済む見込みで、`src/instrumentation-client.ts`（既にある）に組み込める。ハニーポットはタダなので残す。AI が書いた文面の投稿はどれでも止まらず、受信側の迷惑メールフィルタに任せる |
| 12 | 添付 | **画像だけ・最大 3 枚**。ブラウザで 250 万画素までの JPEG に縮小して送り（転送の大きさのため）、**サーバーで `sharp` が読み込んで JPEG に書き出し直したものだけ**を Resend の添付にする。Storage には上げない | スクリーンショットがあると一度で伝わる。メールに付ければ assift に保存場所が増えず、未ログインの人に Storage へ書かせる口も作らない。縮小すれば 3 枚でも Vercel の関数の上限（1 リクエスト 4.5MB）に収まる。種類の確認を先頭のバイトで手書きするのは、先頭だけ画像に見せたファイルを通すので単独では頼れない（OWASP）。書き出し直せば、画像でないものは失敗し、紛れ込んだ余計な中身とメタデータ（位置情報）も消える。ブラウザの縮小を経ずに送られても同じ形になる。`sharp` は Next が既に使っている（`next` の依存。`serverExternalPackages` の既定に入っている） |

### 4.3 フォームの項目

| 項目 | ログイン中 | 未ログイン | 決まり |
| --- | --- | --- | --- |
| 種類 | ○ | ○ | `Select`。「使い方」「料金・契約」「不具合」「退会・データ」「その他」。`topic` で初期値を入れる（課金の画面からは「料金・契約」）。未選択（`null`）に日本語の `{ error }` を付ける |
| メールアドレス | ―（アカウントのものを表示） | ○ | `lib/validation/auth.ts` のメールのスキーマを使い回す |
| 内容 | ○ | ○ | 1〜5,000 文字（§9-4）。エラー番号は本文の初期値に入れず、自動で付ける情報に入れる（消されない） |
| 画像（任意） | ○ | ○ | 3 枚まで（§4.7）。Mantine の `FileButton`。選んだらすぐ縮小し、小さなプレビューと「削除」を出す |
| ハニーポット | ○ | ○ | 人には見えない入力欄（§4.6） |

- 送信ボタンの近くにプライバシーポリシーへのリンクを置く（「送信いただいた内容は、プライバシーポリシーに従って取り扱います」）。同意のチェックボックスは置かない（利用目的は公表済み）
- 完了の画面: 「送信しました。ご入力のアドレス（…）へ返信します。数日たっても届かない場合は、迷惑メールのフォルダをご確認ください」。返信の目安（「〇営業日以内」）は §9-3
- 失敗の画面: 「送信できませんでした。時間をおいてもう一度お試しください。」に続けて、**このときだけ**アドレスを出す（「解決しない場合は support@assift.com へ」）。Client の state でしか描かれないので、クローラーは読まない
- 送信が 60 秒を過ぎても終わらないときも、ボタンの下にアドレスを出す（待つのはやめない。§10.4 の 19 回目）

### 4.4 自動で付ける情報（ログイン中だけ）

問い合わせの文のあと、区切り線（`-` を 40 個）に続けて書く。**サーバーで確かめた値だけ**を書く（URL から来た値はそのまま信じない）。

利用者は問い合わせの文に区切り線と偽の「アカウント: …」を書けるので、本物は**いちばん最後の区切り線のあと**になる。
レビューで入力の各行の頭に `| ` を付けて区別したが、起きる頻度の低さに比べて、すべての正常なメールに印が出る違和感が大きいので外した（§10.4 の 21 回目）。
代わりに運用で守る: **アカウントに関わる依頼（退会・データの削除・契約の変更）は、返信先とアカウントのアドレスが一致するかを確かめてから受ける**（032 §3「運用の決まり」）。

| 項目 | 出どころ | 確かめ方 |
| --- | --- | --- |
| ユーザー id・メールアドレス | `getAuthUser()`（JWT） | ― |
| 店舗 | `?tenant=` | `createClient()`（RLS）で `tenants` を読み、見えたときだけ id と名前を書く。見えなければ書かない |
| エラー番号 | `?digest=` | 英数字だけ・長さの上限。エラー画面から来たときだけ付く |
| ブラウザ | `headers()` の `user-agent` | 長さの上限で切る |

- 未ログインで送ったときは「未ログイン」とブラウザだけを書く（`?tenant=` があっても読まない。見えないので）。エラー番号は未ログインでも付ける（ログイン画面などのエラーもありうる）
- 返信の引用で相手に戻っても困らない値だけにする（本人の情報）。Stripe の Customer id・管理画面の URL・内部のメモは入れない

### 4.5 メール

| 項目 | 値 |
| --- | --- |
| `from` | `assift <noreply@assift.com>`（024 で検証済みの差出人。認証メールと同じ） |
| `to` | `CONTACT_INBOX`（本番は `support@assift.com`） |
| `reply_to` | 相手のアドレス（ログイン中はアカウントのもの） |
| `subject` | `[お問い合わせ] {種類}：{内容の先頭 30 文字}（#{requestId の頭 8 文字}）`。改行・制御文字は空白に置き換える。受付番号で、同じ件名の別の問い合わせが Gmail で 1 つのスレッドにまとまらない |
| `text` | 返信先 + 内容 + 区切り線 + 種類・自動で付ける情報（添付の枚数も書く） |
| `attachments` | `[{ filename: 'image-1.jpg', content: <base64> }, …]`（§4.7） |
| `Idempotency-Key` | `contact/{requestId}/{送る中身の SHA-256}`（§10.2-1）。`requestId` はフォームを開いたときにクライアントが作る uuid（`uuid` の v4）で、送信の連打・やり直しで二重に届かない（Resend は 24 時間、同じ鍵の再送を 1 通にする）。中身を直して送り直すと別の鍵になる（同じ鍵で中身が違うと Resend は 409 で断る） |

- Gmail は差出人と件名でスレッドをまとめるので、件名に内容の先頭を入れて問い合わせごとに分ける。Missive は件名ではなく Reply-To などのヘッダで会話をまとめる（032 §4-3 で確かめる）
- 受信箱では差出人（`noreply@`）が連絡先として出るので、誰からかは件名と本文の先頭（「返信先: …」）で分かるようにする
- **Missive で返信したときの宛先が Reply-To になるかは、公式ドキュメントに書かれていない**。032 §4-1（10/25〜10/26）で確かめ、ならなければ §9-6 で設計し直してから実装する
- 受信箱で迷惑な投稿を「Mark as spam」で弾くと `noreply@assift.com` がブロックされ、以後のフォームが届かなくなる（032 §3 の運用の決まり）

### 4.6 迷惑な投稿の対策

ログインの有無にかかわらず、すべての送信に掛ける。

| 段 | 内容 | 失敗したとき |
| --- | --- | --- |
| 1. BotID | `next.config.ts` を `withBotId()` で包む（判定のスクリプトを自分のドメインから配るリライトが足される）。`src/instrumentation-client.ts` で `initBotId({ protect: [{ path: '/contact', method: 'POST' }] })`。Action の先頭で `checkBotId()` | 失敗を返して送らない（「送信できませんでした」。人が誤判定されたときにやり直せるように、黙って成功にしない） |
| 2. 回数の制限 | **Vercel Firewall のレート制限**（IP ごとに 10 分で 5 回など）。コードは書かない。merge のあとに利用者が作る。**条件はパスではなく「POST かつ `Content-Type` に `multipart/form-data` を含む」**（§10.4 の 4 回目） | Vercel が 429 を返す。Action は失敗の表示になる |
| 3. ハニーポット | 画面の外に置いた入力欄（`hp_ref_code`。自動入力が埋めそうな語を避ける。送るときに DOM の値を読む。`tabIndex={-1}`・`autoComplete="off"`・`aria-hidden`。`type="hidden"` にはしない）。値が入っていればボット | **成功を返して送らない**（ボットに判定の手がかりを与えない） |

- BotID は Basic（無料）から始める。Deep Analysis（Pro で 1,000 回の判定ごとに $1）は送信のときだけ走るので、月 100 件でも約 $0.1。Basic で止まらない投稿が目立ったら有効にする（§9-7）
- BotID と CSP（022）: スクリプトは `instrumentation-client` から `createElement` で足されるので `'strict-dynamic'` で通り、送信も同一オリジン（`connect-src 'self'`）。`npm run build && npm run start` で `securitypolicyviolation` が 0 件（本物の判定のスクリプトを中継して確かめた。§10.3）
- BotID の中継のパスは proxy の matcher から**前方一致で外した**（完全一致の決まりの例外。リライトで配下がすべて Vercel へ行き、Next の 404 の HTML にならない。§10.2-4）
- 開発では `initBotId` を呼ばない（判定のスクリプトが読めず送信が止まるため）。サーバーの `checkBotId()` は Vercel の外では判定を飛ばす。Vercel の上では判定の失敗で止める（§10.2-2）
- 2 は Pro の Firewall でレート制限のルールが使えるか、料金がかかるかを確かめる（§9-2）。使えなければ、回数を数える置き場（DB の表など）が要るので別に決める
- **Server Action はどのパスにも POST で呼べる**（`Next-Action` のヘッダに Action の id を付ければ、`/` にも `/terms` にも届く）。`/contact` のパスで絞るルールはすり抜けられる。
  一方、ほかの Action は `FormData` を使わない（AGENTS.md「Server Actions」）ので、本文が `multipart/form-data` になるのはお問い合わせだけ。ルールはこれで絞る（ほかの Action・ページの表示を巻き込まない）。
  BotID はパスに依らない: サーバーの `checkBotId()` は Action の中で毎回走り、`/contact` 以外のパスに送られた POST には判定のヘッダが付かないので、ボットと判定される（§8 でプレビューで確かめる）

### 4.7 添付

**ブラウザ**（転送を小さくするため。守りはサーバー）

| 項目 | 決まり |
| --- | --- |
| 選べる種類 | PNG・JPEG・WebP（ファイル選択の `accept`） |
| 枚数 | 3 枚まで |
| 縮小 | **画素数 250 万まで**（長い辺は 8,000px まで）・JPEG の品質 0.85。1 枚 1.5MB を超えたら 0.7 → 0.5 で書き出し直し、それでも超えたら外す（`createImageBitmap` + `canvas.toBlob`）。計算は `lib/contact/scale.ts` をサーバーと共有。長い辺で縮めると縦長のスクリーンショットの幅が数十 px になり読めない（§10.4 の 15 回目）。1,170 × 20,000 のスクリーンショットは 382 × 6,537・約 730KB |
| プレビュー | `FileReader.readAsDataURL` の `data:` の URL で描く。`URL.createObjectURL`（`blob:`）は使わない（`img-src` に `blob:` が無い。022） |
| iPhone の写真（HEIC） | iOS の Safari は `accept` に HEIC が無いと JPEG に変えて渡すことが多い。`createImageBitmap` で読めるかを実機で確かめる（§8）。読めなければ「この画像は添付できません」と出す |

**サーバー**（`lib/contact/attachments.ts`）

| 項目 | 決まり |
| --- | --- |
| 枚数・大きさ | 3 枚まで・1 枚 1.5MB・合計 3.5MB（`bodySizeLimit` の 4MB から区切りと本文の分を残す）。超えたら書き出す前に失敗にする |
| 種類 | `sharp(buffer).metadata()`（ヘッダだけ読む）の `format` が `jpeg` / `png` / `webp` のものだけ通す。`sharp` は SVG・TIFF・GIF・HEIF なども読めるので、**画素を読む前に種類で絞る**（特に SVG は画像の形をした文書） |
| 書き出し直し | 1 枚ずつ `sharp(buffer, { limitInputPixels: 3000 * 3000 })` → `metadata()` の形式と `autoOrient` の大きさ → `.rotate().resize(contactImageSize(…))`（画素数 250 万まで）`.flatten({ background: '#ffffff' }).jpeg({ quality: 85 }).toBuffer()`。1 枚 1.5MB を超えたらブラウザと同じく 70 → 50 で書き出し直す（ブラウザが品質を下げて収めた画像を膨らませない）。読めなければ例外 → 「この画像は添付できません」 |
| メタデータ | `sharp` は既定で書き出しにメタデータを付けない（`rotate()` で向きを画素に反映してから落とす）。位置情報は残らない |
| 解凍爆弾 | `limitInputPixels`（3,000 × 3,000 = 900 万画素。ブラウザは 250 万画素に縮めて送るので余裕がある。§10.4 の 8 回目で 4,000 万から下げた）。超えたら「大きすぎる」 |
| 送るファイル名 | サーバーが決める（`image-1.jpg`…）。利用者のファイル名は使わない（制御文字・長さ・個人名の混入を避ける） |

- **依存**: `sharp` を `package.json` の `dependencies` に足す（`next` の optionalDependencies と同じ範囲 `^0.35.4`。重複させない）。`serverExternalPackages` の既定に入っているので Next の設定は要らない。
  本番の関数に native のファイルが入るかを `npm run build` の `.nft.json`（`/contact` のページ）で確かめる（AGENTS.md「実行時に読むファイル」）。関数が大きくなり最初の起動が少し遅くなるのは受け入れる
- **Server Action の大きさの上限**: Next の既定は 1MB。`next.config.ts` の `experimental.serverActions.bodySizeLimit` を `'4mb'` にする。**全部の Server Action に効く**（ほかの Action も 4MB までのリクエストを受ける）。Vercel の関数の上限（4.5MB）より小さく、各 Action は Zod で中身を確かめるので害は小さい。受け入れたトレードオフとする
- Resend の添付の上限（1 通 40MB）には余裕で収まる

## 8. 確かめ方

- Vitest:
  - スキーマ（日本語のエラー・上限）、件名の改行と制御文字の置き換え、`?digest=` の判定、`contactHref`

### 10.2 実装で決めたこと

1. **`Idempotency-Key` に本文の指紋を入れた**（§4.5 の `contact/{requestId}` から変えた）: 鍵が同じで中身が違うと Resend は 409 で断る。
   失敗のあとに本文を直して送り直すと届かなくなるので、同じ中身の連打・送り直しだけを 1 通にまとめる
2. **BotID の判定そのものが失敗したら、Vercel の上では止める**（`process.env.VERCEL`。§10.4 の 5 回目で fail-open から変えた）: OIDC の設定漏れ・Vercel の障害で例外になる。
   Server Action はどのパスにも POST で呼べるので、通すと残る守りはハニーポットだけになる。止めても、画面の失敗の表示がアドレスを案内する。Vercel の外（ローカルの `next start`）では判定できないので通す
3. **開発では `initBotId` を呼ばない**: サーバーの `checkBotId()` は開発（`NODE_ENV !== 'production'`）で常に人と答える。一方クライアントは判定のスクリプトを読み終えるまで `fetch` を止めるので、読めないと送信そのものが止まる（この環境では `api.vercel.com` に出られず実際に止まった）。
   **本番でもスクリプトが読めなければ送信は失敗する**（BotID の作り）。そのときはフォームの失敗の表示がアドレスを案内する（§4.3）
4. **proxy の matcher から BotID の中継のパスを前方一致で外した**（完全一致の決まりの例外）: `withBotId` のリライトが配下をすべて Vercel へ中継するので、Next の 404 の HTML にはならない。
   通すと Supabase の cookie の更新が判定のたびに走り、proxy の CSP（`frame-ancestors 'none'`）と BotID 自身のヘッダ（`frame-ancestors 'self'`）が重なる
5. **透過の画像は白を敷く**（ブラウザの縮小とサーバーの書き出しの両方）。JPEG に透過は無く、そのままだと黒くなる
6. 返信の目安は書かない・特商法の表記のアドレスは残す・回数の制限は Firewall で後から（§9 の決定）

### 10.5 ログイン中のサイトのヘッダー（2026-10-19）

ログイン中に `/contact` を開くと、LP のヘッダー（「ログイン」「無料ではじめる」）が出て違和感がある、という利用者の指摘から入れた。
規約・ポリシー・特商法の表記もフッターやアプリのメニューからログイン中に開くので同じ（LP の `/` は proxy が `/tenants` へ送る）。

- `(site)/layout.tsx` が `getAuthUser()`（JWT）を読み、`SiteHeader` に `loggedIn` を渡す。ログイン中は LP の見出しへのリンク（できること・料金・よくある質問）と「ログイン」「無料ではじめる」を出さず、「アプリを開く」（`/tenants`。直近の店舗へ送られる）1 つにする。
  CSP の nonce で全ページがもともと動的描画なので、静的化を失うものは無い
- `/contact` の上の「← 店舗に戻る」のリンクは、ヘッダーと重なるので外した

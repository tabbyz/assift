## 1. 目的と完了条件

### 目的

`/terms` を作る。v1 の規約は引き継がず、一から書く。

よくある SaaS の規約は「甲は乙に対し…」「本規約に定めのない事項については…」のような文体で、**読まれない前提**で書かれている。
しかし規約は「何をしてよくて、何が起きたら誰の責任か」をユーザーと決める文書で、こちらとしては**読んで理解したうえで**使ってほしい。
そこで法的な効力を保ったまま、ふだんの言葉で書く。

### 完了条件

- [ ] 各条の本文のあとの「要約」で、その条の要点が分かる

- [ ] スマホ幅で読める

## 2. 文章の方針

| 方針 | 具体 |
| --- | --- |
| 人称 | 「甲 / 乙」「当社 / 利用者」ではなく **「私たち」 / 「あなた」** |
| 文体 | です・ます。1 文 1 つのこと。箇条書きを使う |
| 法律用語 | 使うときは言い換えを添える（「重大な過失（ひどい不注意）」） |
| 要約 | 各条の本文のあとに「要約」。**本文が正式**であることを明記する |
| 約束は具体的に | 守れる約束は日数で書く（サービス終了 30 日前）。規約の変更は運用上日数を約束しにくいので「始まる前に」とする |
| 不利なことも書く | 共有リンクは誰でも見られる・AI は間違える・消したデータは戻せない、を目立たない場所に隠さない |

法的に落とせないもの（定型約款・消費者契約法）:

- **同意の取り方**: サインアップのチェックで規約に同意する（民法 548 条の 2。定型約款）
- **変更**: 内容と効力発生日を事前に周知する（548 条の 4）。重要な変更はメールでも知らせる
- **免責**: 全部免責は無効（消費者契約法 8 条）。「私たちの故意・重大な過失を除き」を明記し、範囲は**直接の損害**に限る。
  「法令が許す限り」のような曖昧な書き方（サルベージ条項。2023 年改正で軽過失の一部免責は明確性が必要）はしない

## 3. assift に固有の論点（実装との突き合わせ）

| 論点 | 実装 | 規約での書き方 |
| --- | --- | --- |
| スタッフの個人情報 | 店長がスタッフ名・勤務条件を入れる | 入れるのは店舗側の判断と責任。スタッフに伝えること。**健康状態などの要配慮情報は入れない**（AI への指示・制約のメモに書かれうる） |
| 共有リンク | 8 文字のコード。未ログインで開ける。終了日の 6 日後まで公開（`lib/shares/expiry.ts`）。`noindex` | URL を知っていれば誰でも見られる。終了日から 7 日目に自動で見られなくなる。いつでも止められる |
| AI | 自動アサインはスタッフ名・勤務条件・期間のシフトを OpenAI に送る（`AssistModal` の注記） | 「AI を使う機能」として広めに書く（送るデータは例示、提供元は OpenAI / Anthropic / Google の 3 社を「いずれか」として併記）。学習に使われないこと。結果は確認してから使う |
| 労務 | 制約は「なるべく」も含め守れないことがある | 労働時間などの法令に合っているかの判断は店舗。assift はそれを保証しない |
| 料金 | v1 と同じくフリーミアム（無料プラン + 月額の有料プラン。v1 は 10 人まで無料） | 申し込んだときだけ料金がかかる。いつでも解約でき、無料プランに戻る。支払い済みは返さない。料金・無料の範囲の変更は始まる前に知らせる。不利な変更は新しい料金になる月の前に知らせる |
| 退会 | `deleteAccount()` → `auth.users` 削除 → `profiles` → `tenants` → 配下が cascade | アカウント画面からいつでも。店舗・シフト表もすべて消え、戻せない |

## 4. 実装

- `src/app/(public)/terms/page.tsx`（Server）。メタデータ `title: '利用規約'`
- 本文は `_components/articles.tsx` に `{ id, title, summary, body }` の配列で持つ。`summary` は本文のあとに「要約」として描く
- 運営者名・連絡先・制定日・裁判所は `_components/terms.ts` の定数（未確定の値を 1 か所に集める。§6）
- Server Component なので Mantine はドット記法を使わない（`ListItem` を import）。ページ内リンクは素の `href="#…"`

## 5. やらないこと

- プライバシーポリシー（`/privacy`）・特商法表記（`/law`）。規約からはリンクだけ張る（`/privacy` は別途）
- 規約の版の記録（同意した版を DB に残す）。変更の周知は 548 条の 4 の周知で足りる。必要になったら `profiles` に列を足す
- フッター。LP（未実装）と合わせて決める
- 版の管理と改定の予告。初回の公開時点では版が 1 つなので、**最初の改定のときに作る**（§5.1）

### 5.1 最初の改定のときに作るもの

第 14 条の「変更が始まる前にこのページで知らせます」を画面で満たす仕組み。例: 10/1 に予告し、10/15 から適用する。

| 日付 | すること |
| --- | --- |
| 予告日（10/1） | 新しい版をデプロイする。不利な変更・大事な変更はメールも送る |
| 予告期間（〜10/14） | `/terms` は**今の版のまま**、冒頭に予告の枠（適用日・主な変更点・新しい版へのリンク・「それまでは今の規約が適用されます。使い続けると同意したものとして扱い、同意できなければそれまでに退会できます」） |
| 適用日（10/15〜） | `/terms` が `todayJst()` で**自動で**新しい版に切り替わる（0 時のデプロイは要らない）。「最終更新」を適用日に、末尾に改定の履歴（日付・変更点の要約・前の版へのリンク） |

実装:

- 本文を版ごとに持つ（`articles.tsx` を版の日付ごとに分け、版に `effectiveOn` と変更点の要約を付ける）
- `/terms` はその日に有効な版を出し、未来の版があるときだけ予告の枠を出す
- `/terms/[version]` で各版を読めるようにする（登録したときの規約を後から確かめられる）
- メールの一斉送信の仕組みは別途（いまは無い）

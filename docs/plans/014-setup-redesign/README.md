## 1. 目的と完了条件

### 目的

- 新しく登録した人が、**白紙から考えずに**数分で自分の店のシフト表にたどり着ける
- 初回に聞くのは「すぐ答えられて、最初のシフト表が変わるもの」だけにする。ほかは既定値にして、必要になったときに聞く
- 途中でやめても、入力した内容が残り、**続きのステップから再開**できる
- 設定中に「できあがるシフト表」を見せ、勤務パターンやスタッフが表のどこに出るかを見た目で分かるようにする

### 完了条件

- 新規ユーザー: ログイン → `/tenants/new`（ステップ 1）→ `/tenants/<id>/setup`（ステップ 2・3）→ 完成 → `/shifts`。
  標準的な店（勤務 5・スタッフ 10）で、押す回数は 10 回以下（店名と名前の入力を除く）
- ステップ 1 の「次へ」で店舗ができ、ステップ 2 の「次へ」で勤務が保存される。どこで閉じても、`/tenants/<id>` を開くと続きのステップに着地する
- 完了した店舗は、勤務やスタッフを全部消しても初期設定に戻されない（`setup_completed_at`）。
  完了済みで勤務または在籍スタッフが 0 のときは、シフト表に 1 行の案内と設定へのリンクを出す（§5.9）
- スタッフが 1 人でもいる店舗（退職者を含む）は、初期設定の書き込み（勤務の置き換え・スタッフの作成）を DB が拒む
- 準備中の店舗では、シフト表・設定画面を開いても `/setup` に送られる。ヘッダーの店舗切替に「準備中」と出る
- 準備中の店舗を初期設定の画面から削除できる
- ステップ 1 のあとにブラウザの「戻る」を押しても、店舗が二重にできない
- 業種を選ぶと、色・時間・お休みの区分つきの勤務が入った状態で出る。夜勤と明けを両方残すと、夜勤のペアが明けになる
- スタッフは 1 行 1 人で貼り付けられる。10 文字を超える名前は、その行を示して止める。同じ名前は注意を出すだけで止めない
- 作成周期を選べる（既定 1ヶ月）。2 週間・1 週間を選んだときだけ開始曜日を聞き、選ぶまで進めない
- PC 幅（`md` 以上）では右に完成イメージ、スマホ幅では各ステップの下に小さな見本が出る。390px で横スクロールが出ない
- 自動作成を開いたとき、必要人数がどこにも無ければ、勤務ごとの人数をその場で聞いてセットできる（§3.8）
- シフト表を初めて開いたとき、最初のマスに「マスを押すと、勤務を入れられます」を 1 回だけ出す
- `tutorial/*` と `SetupNotice` の STEP カードが消え、v1 の `/tenants/<token>/tutorial/...` は店舗のトップへ送られる
- `npm run format:check` / `lint` / `typecheck` / `test` / `build` と `npx supabase test db` が通る。`db reset` と `gen types` を行う

## 2. 確認済みの前提

### 2.1 いまの流れと課題

Artifact の「現状の分析と課題」に詳細がある。要点:

- 6 画面。うち「はじめに」「完了」は読むだけ
- チュートリアルは設定画面の `PatternForm` / `StaffForm` をそのまま埋め込む（005 §3.4、006 §3.5）。
  勤務 5・スタッフ 10 の店で、画面に出る入力欄はのべ約 290 個、押すボタンは 20 回
- 1 件ずつしか登録できない。登録したものはカンマ区切りの文字で出るだけで、その場で直せない
- 色の既定が白（`DEFAULT_PATTERN_COLOR`）。選ばずに進むと表で見分けがつかない
- 完了の判定は `getTutorialStatus()`（勤務 1 件以上 かつ 在籍スタッフ 1 人以上）。
  運用中にスタッフを全員退職させると、店舗を開いたときにチュートリアルへ飛ばされる
- シフト表には別の案内（`SetupNotice`）があり、同じ目的の案内が 2 系統ある

### 2.2 DB の上限（テンプレートと入力の制約になる）

| 列 | 上限 | 出どころ |
| --- | --- | --- |
| `tenants.name` | 1〜20 文字 | `TENANT_NAME_MAX_LENGTH` |
| `patterns.name` | 1〜6 文字 | `PATTERN_NAME_MAX_LENGTH` |
| `patterns.description` | 10 文字まで | `PATTERN_DESCRIPTION_MAX_LENGTH`。**`9:00〜17:00` は 10 文字だが `17:00〜23:00` は 11 文字で入らない** |
| `staffs.name` | 1〜10 文字 | `STAFF_NAME_MAX_LENGTH` |
| `patterns.pair_pattern_id` | 同じ店舗の勤務 | 複合 FK `(pair_pattern_id, tenant_id)` |

`staffs` は `available_wdays`（全曜日）と `max_work_week`（5）が DB の既定値を持つ。初期設定ではこの既定値のまま作る。

### 2.3 作成周期と週の始まりが効く場所

- `shift_cycle`: 表の期間（`dateRange()`）、前後の移動、コピー、共有、エクスポート、自動作成の期間
- `start_of_week`: ①週・2 週の表がどの曜日から始まるか（`dateRange()`）、②自動作成が週の上限を数える区切り（`weekDates()`）。
  1ヶ月・半月の表は日付が並ぶだけなので、見た目は変わらない
- シフトは日付ごとの行なので、あとで周期や週の始まりを変えても消えない
- 1ヶ月の表は「開始日から 1ヶ月」だが、`?start=` が無いときの開始日は毎回「月初」（`defaultStart()`）。
  締め日に合わせて「16 日〜翌 15 日」で作る店は、開くたびに開始日を選び直すことになる（§7 で別課題にする）

### 2.4 自動作成と必要人数

`AssistModal` は必要人数が 1 件も無いと「必要人数が設定されていません」と「デフォルト人数をセット」を出す。
ただしテンプレートで作った勤務は `default_required_nums = {}` なので、このボタンを押しても 0 人の行が入るだけで
（`defaultRequiredNum()` が空欄を 0 にする）、`hasRequiredNums()` は 1 人以上の行しか数えないため「必要人数なし」のまま変わらない。
「必要になったときに聞く」と約束する以上、ここに入力の口が要る（§3.8）。

### 3.2 業種テンプレートは仮の値で始める — **決定（2026-10-04）**

### 3.3 途中でやめても再開できる — **決定（2026-10-04）**

ステップごとに保存する（§3.6）。続きの位置はデータから決める（§5.6）。

保存の規則は 1 つにそろえる: **「次へ」「これで完成」を押した内容は DB に保存され、どの端末からでも続きを開ける。
押す前の入力は、普通のフォームと同じく保存されない。** ブラウザに下書きは残さない（`localStorage` の下書きはやめる。
同じ端末でしか効かず「DB に保存されている」という説明とずれるうえ、共用 PC にスタッフ名が残る。2026-10-04 決定）。
例外は「あとで続ける」で、ステップ 2 の編集は保存してから抜ける（§4.5）。

### 3.4 初回に聞くのは必要最小限 — **決定（2026-10-04）**

基準は「店長がすぐ答えられるか」かつ「答えで最初に開くシフト表が変わるか」。

| 項目 | 初回 | 扱い |
| --- | --- | --- |
| 店名 | 聞く（必須） | ステップ 1 |
| 作成周期 | 聞く（1 タップ） | ステップ 1。「1ヶ月」を選んだ状態で出す |
| 週の始まり | 2 週間・1 週間のときだけ聞く | ステップ 1。**どの曜日も選んでいない状態で出す**（根拠になるデータが無く、違う曜日を選んでおくと気づかず進まれる）。1ヶ月・半月の店は日曜のまま（労基法の「1 週間」も、就業規則に定めがなければ日曜〜土曜の暦週とされる。昭和 63 年 1 月 1 日 基発第 1 号。出典の原文までは確かめない。2026-10-04 決定） |

| スタッフ名 | 聞く（1 人以上） | ステップ 3。1 行 1 人 |
| 色・区分・ペア | 聞かない | テンプレートが持つ。足した勤務は使っていない色・「働く日」 |

| 働ける曜日・選べる勤務・週の上限 | 聞かない | DB の既定値（全曜日・全勤務・週 5）。スタッフの画面で変える |
| 制約 | 聞かない | いまと同じく制約の画面 |

### 3.5 PC とスマホで見せ方を分ける — **決定（2026-10-04）**

`md` 以上は 2 カラム（左に入力、右に完成イメージ）。`md` 未満は 1 カラムで、各ステップの下に小さな見本。
コンポーネントは共通にし、出し分けは Mantine の `visibleFrom` / `hiddenFrom` で行う。

### 3.6 完了のフラグを付ける — **決定（2026-10-04）**

`tenants.setup_completed_at timestamptz`（null = 準備中）。続きの位置だけならデータから分かるが、次の 3 つのために付ける。

1. 完了した店舗が初期設定に戻されない（§2.1 の退職の例）
2. ステップ 2 の保存を「置き換え」にできる。準備中の店舗にはスタッフが 1 人もいない（§5.1 の埋め戻しと §5.2 の RPC の検査で守る）。
   シフトはスタッフがいないと作れないので、勤務を全部消して入れ直しても消えるシフトは無い。完了後の置き換えも DB で拒める
3. 離脱した位置と完了までの時間を数えられる

真偽値ではなく日時にする。**どのステップかは保存しない**（データとずれる状態を作らない）。

### 3.7 準備中の店舗のガードは 2 か所に置き、ヘッダーはウィザードが持つ — **推奨**

- `[tenantId]/layout.tsx`: 準備中なら `TenantShell` を描かず、`children` をそのまま返す（ヘッダーはウィザードが描く）。完了なら `TenantShell`
- `shifts/page.tsx` と `settings/layout.tsx`: 準備中なら `/setup` へ `redirect()`
- `setup/page.tsx`: 完了済みなら `/shifts` へ `redirect()`

route group（`(ready)/`）でまとめる案もあるが、`shifts/` と `settings/` を丸ごと移す diff になり、得るものはガード 1 か所ぶんしかない。
layout はパスを知れない（005 §2）ので、`[tenantId]/layout.tsx` で振り分けると `/setup` 自身もループする。

ヘッダーを layout 側に置かない理由: 「あとで続ける」はいまのステップ（ステップ 1 では出さない）と、押したあとの画面の切り替えを
知っている必要があるが、layout はパスもウィザードの状態も知れない。準備中に描かれるのは `/setup` だけ（ほかは redirect）なので、
ウィザードが自分のヘッダー（`SetupHeader`。§5.7）を持てば足りる。

### 3.8 自動作成で必要人数を聞く — **推奨: 本プランに含める（最小の形）**

完成画面で「何人ずつ必要かは、AI で作るときにお聞きします」と書くので、その口を作る。
`AssistModal` で「必要人数が 1 件も無く、どの勤務にもデフォルトが無い」ときだけ、「デフォルト人数をセット」の代わりに
勤務ごとに 1 つの数（全曜日共通、既定 1）を聞き、`default_required_nums` に保存してから期間にセットする。
曜日ごとの人数は、いまの勤務パターンの画面で変える。

- 判定: `ShiftsClient` が持つ勤務（`kind = 'workday'`）の `default_required_nums` がすべて空、かつ `hasRequiredNums()` が false
- 書き込み: `shifts/actions.ts` に `setUniformDefaultRequiredNums({ tenantId, nums: { [patternId]: number } })` を足す。
  いまの `updatePattern` は全項目を受ける形なので使わない。勤務ごとに `default_required_nums` を全曜日・祝日が同じ値の JSON で
  update する（勤務は多くても 20 件なので `Promise.all`。0 行なら `PATTERN_NOT_FOUND_MESSAGE`）。そのあと既存の
  `setDefaultRequiredNums` で表示中の期間に入れる。Zod は `REQUIRED_NUM_MIN` / `MAX` を使う。
  複数の update は 1 トランザクションにならないが、RPC にはしない: 途中で失敗しても、入った勤務の既定値が正しい値で残るだけで、
  もう一度押せば全部そろう（壊れた状態が残らない）。AGENTS.md の「1 文で書けないなら RPC」は、途中で止まると矛盾が残る書き込みのための規則

外すなら、完成画面の文言を「必要な人数は［設定］→［勤務パターン］で入れられます」に変える。

## 4. 画面

プロトタイプ（Artifact の推奨案の行）が見た目の正。文言は §4.8 の原則に合わせる。

### 4.1 ステップ 1: お店のこと（`/tenants/new`）

- 見出し「お店について教えてください」。添え書き「3 つの質問に答えるだけで、シフト表の準備ができます（約 3 分）」
- お店の名前（20 文字。残り文字数を出す）
- 「シフト表は何日分ずつ作りますか？」: 1ヶ月 / 半月 / 2週間 / 1週間 のボタン。1ヶ月を選んだ状態。
  添え書き「迷ったら『1ヶ月』。あとで変えても、入れたシフトは消えません」
- 2 週間・1 週間を選んだときだけ「何曜日から始まりますか？」。PC は月〜日の 7 つ。スマホは「月曜・日曜」を大きく出し、
  「ほかの曜日から始まる」で残りを開く
- 「次へ」で店舗を作って `/tenants/<id>/setup` へ。**移動は `router.replace`**（`push` だとブラウザの「戻る」で
  `/tenants/new` の作成フォームに戻り、もう一度「次へ」を押すと店舗が二重にできる）。
  足りないものは「あと少し：お店の名前を入れてください」をボタンの上に出す（ボタンは押せなくしてよいが、理由を必ず書く）
- 2 店舗目以降は「キャンセル」（→ `/tenants`）を出す
- `/setup` から「もどる」でステップ 1 を開いたときは、`/setup` の中で同じ部品を出し、店舗を更新する（§5.5 の `updateSetupTenant`）。
  この画面の下に「この店舗を削除する」（§4.5）

### 4.2 ステップ 2: 勤務の種類（`/setup`）

- 勤務が 0 件のとき: 「どんなお仕事のお店ですか？」。5 つの大きなボタン（飲食店 / 小売・コンビニ / 介護・医療 / 保育・教育 / その他）。
  各ボタンに「早番・遅番 など」と中身を添える
- 選ぶと「お店で使う勤務にチェックを残してください」。「働く日の勤務」「お休み（勤務日数に数えません）」の 2 群で、
  行全体がチェックのボタン。右の鉛筆で名前と時間を直す・削除する。「お仕事を選びなおす」で業種の選択に戻る
- 夜勤と明けを両方残しているときだけ「夜勤の次の日に『明け』を自動で入れる」スイッチ（既定オン）
- 「ほかの勤務を追加する」: 名前・時間（任意）・働く日 / お休み。色は使っていない色を自動で割り当てる
- 勤務が保存済みで再開したとき・ステップ 3 から戻ったとき: 保存済みの勤務を同じ一覧で出す。
  明けのスイッチは `pair_pattern_id` から戻す（§5.3 の `fromSavedPatterns`）。業種は保存していないので、
  「お仕事を選びなおす」はテンプレートで置き換える旨を確認ダイアログで聞く
- スマホは一覧の下に「シフト表ではこう見えます」（1 行 7 日の見本）
- 「次へ」で勤務を保存（置き換え）してステップ 3 へ

### 4.3 ステップ 3: スタッフ（`/setup`）

- 「働く人の名前を入れてください」。1 行に 1 人。LINE や Excel からの貼り付けを受ける（区切りは §5.4）
- 人数をその場で数える（「8 人」）。10 文字を超える行は、行番号つきでテキストエリアの下に出し、進めない
- 同じ名前は止めない（設定画面も DB も同名を許している。佐藤さんが 2 人いる店は現実にある）。
  「同じ名前が 2 人います（3 行目・7 行目）。区別がつくように直すのがおすすめです」と注意だけ出す。
  2 回貼り付けた間違いは、人数の表示と合わせて気づける
- 入力中の名前はブラウザにも DB にも残さない（§3.3）
- 添え書き「『土日は入れない』などの条件は、スタッフの画面でいつでも設定できます」
- スマホは「シフト表ではこう並びます」（最大 4 人 × 7 日の見本）
- 「これで完成」でスタッフを作り、完了を記録する。**二度押しで 2 回目が `setup completed` になったときは、エラーにせず `/shifts` へ送る**
  （1 回目で完了している）

### 4.4 完成

- 「準備ができました」と、「（店名）のシフト表を、勤務 n 種類・スタッフ n 人で用意しました」
- 「このあと必要になったらお聞きすること」: 何人ずつ必要か（AI で作るとき）。働ける曜日はスタッフの画面で、と添える
- 「シフト表をひらく」→ `/shifts`

### 4.5 あとで続ける・再開

- ステップ 2・3 のヘッダーに「あとで続ける」。押したときのいまのステップの扱い:
  - ステップ 2: 保存していない変更があれば保存（`saveSetupPatterns`）してから抜ける。変更が無ければそのまま抜ける。
    変更があるのに保存できない状態（働く日が 0 件など）のときだけ「いまの変更は保存されません。終わりますか？」と確かめる
  - ステップ 3: テキストエリアに名前が入っていれば「入力した名前は保存されません。終わりますか？」と確かめる（§3.3）。空ならそのまま抜ける
- 抜けると「ここまで保存しました」と、保存済み / 次はここから のチェックリストを出す。
  ほかの店舗があれば、その店舗へのリンクも出す。ログアウトもここから
- この画面とステップ 1 の下に「この店舗を削除する」。設定画面はガードで開けない（§3.7）ので、試しに作って放置した店舗はここでしか消せない。
  確認ダイアログつきで既存の `deleteTenant` を使う（§5.5）
- 次に `/tenants/<id>` を開くと、データから決めたステップに着地し、上に「おかえりなさい。前回の続きから始めます」を出す
  （同じタブでステップを進めてきたかを `sessionStorage` に持ち、無ければ「再開」とみなす。URL に状態を持たない。
  読めない環境では出さないだけで、着地するステップは変わらない）

### 4.6 PC とスマホ

- PC（`md` 以上）: ヘッダーの下に左右 2 カラム。左 480px に入力、右に完成イメージ（店名と期間 → 表 → 凡例）。
  いまのステップに当たる場所（見出し・凡例・スタッフ列）を点線の枠で示す。表のマスの中身は「見本」と明記する。
  `md` の下限（992px）では右は約 500px で、14 日分の表（約 740px）は入らないので、表は枠の中で横にスクロールさせる（ページは横に動かさない）
- スマホ: 1 カラム。上に「n / 3」と 3 分割の進み具合、下に固定の主ボタン
- 完成イメージの表は `src/components/shiftTable/` の `cellStyle` と CSS を使い、本物の表と同じ見た目にする

### 4.7 シフト表の初回案内

- 店舗ごとに 1 回だけ（`localStorage` の `assift-shift-coach:<tenantId>`）。表示中の期間にシフトが 1 件も無いときだけ出す
- 最初のスタッフの期間初日のセルに `Popover`「マスを押すと、勤務を入れられます」。1 つ入れたら「できました。ほかのマスも同じように入れられます」に変えて閉じる

### 4.8 文言の原則

- 仕様の言葉を出さない（「勤務パターン」「パターン区分」「ペア」「作成周期」「自動アサイン」は画面に出さない。設定画面の名前は変えない）
- 見出しは質問文。添え書きは 1 文
- 足りないものは理由を書く（「あと少し：…」）。押せないボタンを黙って置かない
- 「あとで変えられます」と、変えても消えないものを言う

### 4.9 アクセシビリティ

- ステップが変わったら、新しいステップの見出し（`h2`、`tabIndex={-1}`）にフォーカスを移す。スクリーンリーダーが新しい問いを読み上げる
- 業種・作成周期・曜日・勤務の行は `button` + `aria-pressed`。チェックの状態を色だけで示さない（チェック印と取り消し線）
- 主ボタンが押せないときは、理由の文（「あと少し：…」）をボタンの `aria-describedby` に結ぶ
- タップ領域は 44px 以上

## 5. 設計の要点

### 5.1 スキーマ

`supabase/schemas/public/tables/tenants.sql` に列を足す。

```sql
setup_completed_at timestamptz,  -- null = 初期設定の途中（014）
```

完了を取り消せないようにする（取り消すと「準備中」に戻り、初期設定の画面に連れて行かれる）。
RPC は `security invoker` なので列の GRANT では絞れない。`private` に BEFORE UPDATE のトリガを置く:

```sql
-- 一度入った setup_completed_at は変えられない
if old.setup_completed_at is not null and new.setup_completed_at is distinct from old.setup_completed_at then
  raise exception 'setup_completed_at is immutable';
end if;
```

トリガは service_role にも効く。運用でデータを直す必要が出たら、その migration の中でトリガを一時的に外して戻す。

差分 migration は `declarative sync --name setup_completed_at`。生成物の末尾に、pg-delta が作らない 2 つを追記する:

1. 既存の店舗の埋め戻し。**条件は「スタッフが 1 人でもいる（退職者を含む）」**
   ```sql
   update public.tenants t set setup_completed_at = t.created_at
    where setup_completed_at is null
      and exists (select 1 from public.staffs s where s.tenant_id = t.id);
   ```
   いまの完了判定（勤務あり かつ **在籍**スタッフあり）にしない理由: スタッフが全員退職した店（v1 から移る店にありうる）や、
   スタッフはいるが勤務が 0 件の店が「準備中」になり、ステップ 2 の置き換えで勤務と一緒に過去のシフト・必要人数・制約が消える
   （`shifts` / `required_nums` / `restrictions` は勤務に `on delete cascade`）、または「これで完成」でスタッフが二重になる。
   スタッフがいない店舗にはシフトが無い（`shifts` は `staffs` への FK を持つ）ので、この条件なら準備中の店舗に消えて困るデータが無い。
   勤務だけある店舗（スタッフ 0）は準備中のまま残り、ステップ 3 から続きを始められる
2. `supabase/unmanaged/restrict_anon_grants.sql`（関数を足すので）

`seed.sql` は migration のあとに流れるので埋め戻しが効かない。seed の店舗の insert に `setup_completed_at` を明示する。

### 5.2 RPC（`supabase/schemas/public/functions.sql`）

どちらも `security invoker`・`set search_path = ''`・先頭で `tenant not found`・件数を `get diagnostics` で確かめる。
`revoke ... from public` / `grant ... to authenticated`。

どちらも先頭で店舗の行をロックし（`select setup_completed_at from public.tenants where id = p_tenant_id for update`。
見えなければ `tenant not found`）、次の 2 つを確かめる（§3.6 の「準備中の店舗にはスタッフがいない」を、前提ではなく DB で守る）:

- 完了済みなら `raise exception '<関数名>: setup completed'`
- スタッフが 1 人でもいれば（退職者を含む）`raise exception '<関数名>: has staffs'`

ロックする理由: 「これで完成」の二度押しや 2 つのタブから同時に呼ばれると、どちらも「スタッフ 0・準備中」を見てから書き始める。
ロックが無いと、後の方は完了日時の update で §5.1 のトリガに当たって `immutable` で失敗する（データは守られるが、
画面には「処理に失敗しました」が出て、§4.3 の「2 回目はシフト表へ送る」にならない）。勤務の置き換えと完成が同時に走るのも防ぐ。
ロックすれば後の方は前の方の確定を待ってから `setup completed` を受け取る。

**`save_setup_patterns(p_tenant_id uuid, p_patterns jsonb) returns integer`**

- 0 件なら `no patterns`
- その店舗の `patterns` を全部消して入れ直す（上の検査によりスタッフ 0 = シフト 0。消えるのは勤務を参照する `required_nums` / `restrictions` などだけ）
- `p_patterns` は `[{ id, name, description, color_hex, kind, pair_id }]`。`id` は Server Action が `crypto.randomUUID()` で振る
  （ペアを id で書けるようにするため）。`position` は配列の順（`with ordinality`）
- 挿入は 2 段: ペア無しで insert → `pair_id` のある行だけ update。同じ insert の中で自分を参照させない
- 入れた行数が `jsonb_array_length(p_patterns)` と違えば例外

**`complete_setup(p_tenant_id uuid, p_staff_names text[]) returns integer`**

- 勤務が 0 件なら `no patterns`。名前が 0 件なら `no staffs`（完了済み・スタッフありは上の共通の検査）
- `staffs` を名前の順で insert（`position` は順番。曜日・週の上限は DB の既定値）
- 入れたスタッフ × その店舗の全勤務を `staff_patterns` に insert（いまの `createStaff` が全勤務にチェックした状態で作るのと同じ）
- `tenants.setup_completed_at = now()`。1 トランザクション

いまの PostgREST の 3 回往復（insert staffs → staff_patterns → update tenants）にしない理由: 途中で失敗すると
「スタッフはいるが準備中」の店舗が残り、再開時にスタッフが二重になる。

### 5.3 業種テンプレート（`lib/setup/templates.ts`）

仮の値。時間は seed と同じ「9-17時」の書き方にする（`HH:MM〜HH:MM` は 11 文字になり説明欄に入らない）。

### 5.4 名前の分割（`lib/setup/parseStaffNames.ts`）

- 区切り: 改行・タブ（Excel の行をコピーしたとき）・`、` `,` `，`。**空白では区切らない**（「山田 花子」）
- 各行を `trim()`（全角空白も）。空行は捨てる
- 戻り値は `{ names, errors, duplicates }`。`errors` は `{ line, name }`（10 文字超。進めない）。
  `duplicates` は `{ name, lines }`（注意だけ。`names` には両方とも残す）
- 上限は 1 回 100 人（それ以上は「100 人ずつ入れてください」）

### 5.5 Action と検証

| ファイル | Action | 内容 |
| --- | --- | --- |
| `tenants/new/actions.ts` | `createTenant({ name, shiftCycle, startOfWeek })` | 既存を拡張。`startOfWeek` は週・2 週のとき必須（`superRefine`）。1ヶ月・半月のときは送られても無視し、0（日曜）を書く |

| 同上 | `saveSetupPatterns({ tenantId, patterns, pairEnabled })` | Zod → id を振る → `save_setup_patterns`。`refresh()`。`setup completed` は `{ redirectTo: '/tenants/<id>/shifts' }` を返す（古いタブ） |
| 同上 | `completeSetup({ tenantId, names })` | `parseStaffNames` と同じ規則（10 文字・100 人）を Zod でも → `complete_setup` → `revalidatePath('/tenants', 'layout')`。`setup completed` は `{ redirectTo: '/tenants/<id>/shifts' }` を返す（二度押し・古いタブ。§4.3） |
| `[tenantId]/actions.ts`（移動） | `deleteTenant({ tenantId })` | いまの `settings/general/actions.ts` から移す。設定画面と初期設定の両方から呼ぶので、AGENTS.md の「ルートをまたいで使う Action はそのグループ直下」に従う |

- スキーマは `lib/validation/setup.ts`。名前・説明・色・区分は `lib/validation/patterns.ts` / `staffs.ts` の leaf を再利用する
- RPC が `tenant not found` を投げるので、`saveSetupPatterns` / `completeSetup` では `requireTenant()` を呼ばない（AGENTS.md の RPC の項）
- **RPC の例外は `toActionError` では日本語にならない**（`toActionError` が訳すのは Zod と `ActionError` だけで、
  PostgREST のエラーは「処理に失敗しました」になる）。`shifts/actions.ts` の `RPC_MESSAGES` / `failFromRpc()` と同じ形の

  `no staffs` →「名前を 1 人以上入れてください」、`has staffs` →「この店舗はすでに使われているため、初期設定では変更できません」
  （通常の流れでは起きない）。`setup completed` は上のとおり例外にせず、3 つの Action とも `/shifts` へ送る。

  `failFromRpc` の共通化（`lib/actions/`）は 2 か所目で、実装時に判断する
- Server Action をページから Client に props で渡す（`src/components/setup/` から route の `actions.ts` を import しない）

- `complete_setup`: スタッフと `staff_patterns`（人数 × 勤務数）ができ、`setup_completed_at` が入る / 2 回目は `setup completed`
  （`immutable` ではない）/ 勤務 0 件は例外 / スタッフがいれば `has staffs` / 他テナントは例外 / anon は 42501
- 同時実行（ロック）は pgTAP では 1 接続しか持てず試せないので、手動で確かめる（§6.3）
- `select plan(n)` を増やす

### 6.3 手動（ローカル）

- 新規ユーザーで 5 業種を一巡（PC 幅・390px）
- ステップ 1 のあと / ステップ 2 のあとでタブを閉じ、`/tenants` から開き直して続きに着地する（別の端末・ブラウザからも）
- ステップ 1 の「次へ」のあとにブラウザの「戻る」を押しても、作成フォームに戻らない（店舗が二重にならない）
- ステップ 2 でチェックを外して「あとで続ける」→ 開き直すと外したままになっている
- 「これで完成」を素早く 2 回押しても、エラーが出ずにシフト表へ着く。2 つのタブで同時に押しても、スタッフは 1 組だけで、
  後のタブもシフト表へ着く（`psql` 2 本で `begin; select complete_setup(...)` を交互に流して、後の方が待ってから `setup completed` になることも見る）
- 完成させたあと、別のタブに残っていたステップ 1 で「次へ」を押すと、店舗を書き換えずにシフト表へ着く
- 準備中の店舗を「この店舗を削除する」で消せる
- 同じ名前を 2 行入れると注意が出て、そのまま完成できる
- 2 週間 + 月曜始まりで作り、シフト表が月曜から始まる
- 完了後にスタッフを全員退職させても `/setup` に戻されず、シフト表に「在籍しているスタッフがいません」の 1 行が出る
- 2 週間・月曜で作ったあと「もどる」で 1ヶ月に変えると、店舗情報の週の始まりが日曜になっている
- 自動作成を開き、必要人数を聞かれて入れると表示中の期間にセットされ、勤務パターンの画面の全曜日にも入っている
- 準備中の店舗で `/shifts`・`/settings/staffs` を直接開くと `/setup` に送られる
- `npm run build` が通る（`redirects()` を足すため）

## 7. スコープ外（申し送り）

- **締め日に合わせた開始日**（「毎月 16 日から」）。いまは開くたびに月初に戻る。店舗の設定に「毎月何日から」を足すかを別に検討する
- 2 店舗目を「いまの店舗からコピーして作る」。2 店舗目以降の手間はここで大きく減るが、コピーの範囲（制約・既定の必要人数など）を詰める必要がある
- 業種テンプレートを実データから見直す（015 の移行で v1 のデータが入ったあと）
- 完了率・離脱位置の計測（`setup_completed_at` と各ステップのデータの有無から出せるが、集計の画面は作らない）
- スタッフの働ける曜日などを、自動作成の前に確かめる口（§3.8 は必要人数だけ）

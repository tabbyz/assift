## 1. 目的と完了条件

サイトに `support@assift.com` を載せるのをやめ、問い合わせの入口を**フォーム**に絞る。届いた問い合わせは **Missive**（iOS アプリ）で受けて返す。

狙いは 2 つ。迷惑メールを増やさないこと（新しく集められるのを防ぐ。もう出回っている分は減らない。§3-1）と、問い合わせに要る情報（誰の・どの店舗の・どの画面の・エラー番号）を最初から揃えること。

- [ ] `/contact` から送ると、Missive に 1 件の会話として届き、Missive から返すと**相手のアドレスに**届く（Reply-To。§4.5・§8）
- [ ] ログイン中に送ると、アカウント・店舗・開いていた画面・エラー番号が本文の末尾に自動で付く（§4.4）
- [ ] 未ログインのフォームに、ボット対策（ハニーポット・時間）と回数の制限が掛かっている（§4.6）
- [ ] サイトの `mailto:` が、§4.8 の表のとおりフォームへのリンクに置き換わっている（残すのは表のとおり）
- [ ] CSP（022）を変えずに動く（外部のスクリプト・iframe を足さない）
- [ ] プライバシーポリシー（委託先に Missive・お問い合わせの内容に自動で付く情報）が実装と食い違わない（§6）
- [ ] `lint` / `typecheck` / `test` が通る（スキーマは触らないので `supabase test db` は変化なし）

- **AI による自動応答**（お客さんに AI が答える機能）: 件数が増えてから検討する
- **添付ファイル**（スクリーンショット）: Storage・サイズの制限・ウイルスの扱いが要る。当面は返信のメールで送ってもらう（§9-6）
- **問い合わせの DB への保存**: 個人情報の置き場を増やさない。送れなければ画面に失敗を返し、利用者がやり直す（§3-6）
- **受け付けの自動返信メール**: 未ログインのフォームから任意のアドレスへメールを送れる口になる（§3-7）
- **Cloudflare Turnstile などの CAPTCHA**: 迷惑な投稿が目立ってから足す（CSP の変更が要る。§4.6）
- **`info@assift.com` の廃止**: v1 からの問い合わせを受けるため残す（016-terms §7 のまま）

## 3. 決定（案。2026-10-18）

| # | 項目 | 案 | 理由 |
| --- | --- | --- | --- |
| 1 | アドレスを載せる場所 | **特商法の表記と global-error だけに残す**。ほかはフォームへのリンク（§4.8） | アドレスは規約・ポリシー・030 の告知・Stripe の公開情報で既に出回っており、消しても届く迷惑メールは減らない。新しく集められるのを減らすのが目的。特商法の表記は法令の確認まで残す（§9-2）。global-error はアプリが落ちたとき（フォームも動かない）にしか描かれず、クローラーが読まない |
| 2 | 受信箱 | **Missive**（Productive を想定。§5） | iOS / Android / Mac にアプリがある。自分の OpenAI の鍵で AI の下書きを上乗せなしで使える。1 人で対応する前提に合う（2026-10-18 の比較） |
| 3 | フォームから受信箱への渡し方 | **メール**（Resend で `support@assift.com` へ送る）。Missive の API は使わない | 受信箱の SaaS を替えても転送先を変えるだけで済む。Missive の API は Productive 以上で、縛られる |
| 4 | ページ | **`/contact` の 1 つ**（`(public)/(site)/contact`）。ログインの有無で中身を変える | 入口が 1 つなら案内が簡単。ログイン中に (site) のヘッダーの「ログイン」を押しても proxy が `/tenants` へ送るので害は無い（`GUEST_ONLY_PATHS`） |
| 5 | ログイン中の返信先 | アカウントのメールアドレスを使い、入力させない | 本人確認が済んだアドレスにしか返さない。打ち間違いが無い |
| 6 | 保存 | DB に保存しない。送信の失敗は画面に返す | §2。やり直しで二重に届かないよう `Idempotency-Key` を付ける（§4.5） |
| 7 | 自動返信 | **送らない**。完了の画面に「ご入力のアドレスへ返信します」と書く | 未ログインのフォームに他人のアドレスを入れると、私たちから他人へメールを送れてしまう（踏み台）。バウンス・迷惑メールの報告が増えると Resend が送信を止め、**認証メールまで止まる**（030 §6.3） |
| 8 | メールの形式 | **テキストだけ**（HTML を作らない） | 自分の受信箱に送るだけで、見た目は要らない。利用者の入力を HTML に埋め込まないので、エスケープの漏れが起きない |
| 9 | 自動で付ける情報 | ユーザー id・メールアドレス・店舗（id と名前。RLS で見えるものだけ）・開いていた画面・エラー番号・ブラウザ（User-Agent） | 契約の状態はユーザー id から管理画面（020）で引けるので本文に入れない。Stripe の id など、本人に見せない値は入れない（返信の引用で相手に戻りうる。§4.4） |
| 10 | 環境 | 送るのは `RESEND_API_KEY` と `CONTACT_INBOX` があるときだけ。開発で無ければコンソールに出して成功にする | プレビューから本番の受信箱に届かないようにする（§4.7） |

## 4. 設計

### 4.1 流れ

```
ログイン中（アプリの各所のリンク: ?tenant=…&from=…&digest=…）─┐
                                                              ├→ /contact → sendContact（Server Action）
未ログイン（フッター・LP）───────────────────────────────────┘        ├ ボット対策（§4.6）→ Zod → 自動で付ける情報（§4.4）
                                                                     └ Resend（POST /emails）→ support@assift.com（Google Workspace）→ Missive
                                                                          差出人 noreply@assift.com / Reply-To = 相手のアドレス
```

### 4.2 ファイル

### 4.3 フォームの項目

| 項目 | ログイン中 | 未ログイン | 決まり |
| --- | --- | --- | --- |
| 種類 | ○ | ○ | `Select`。「使い方」「料金・契約」「不具合」「退会・データ」「その他」。`topic` で初期値を入れる（課金の画面からは「料金・契約」）。未選択（`null`）に日本語の `{ error }` を付ける |
| メールアドレス | ―（アカウントのものを表示） | ○ | `lib/validation/auth.ts` のメールのスキーマを使い回す |
| 内容 | ○ | ○ | 1〜5,000 文字（§9-5）。`digest` があれば「エラー番号: …」を本文の初期値に入れるのではなく、自動で付ける情報に入れる（消されない） |
| ハニーポット | ―（ログイン中は見ない） | ○ | 人には見えない入力欄（§4.6） |

- 送信ボタンの近くにプライバシーポリシーへのリンクを置く（「送信いただいた内容は、プライバシーポリシーに従って取り扱います」）。同意のチェックボックスは置かない（利用目的は公表済み）
- 完了の画面: 「送信しました。ご入力のアドレス（…）へ返信します。数日たっても届かない場合は、迷惑メールのフォルダをご確認ください」。返信の目安（「〇営業日以内」）は §9-4
- 失敗の画面: 「送信できませんでした。時間をおいてもう一度お試しください。」に続けて、**このときだけ**アドレスを出す（「解決しない場合は support@assift.com へ」）。Client の state でしか描かれないので、クローラーは読まない

### 4.4 自動で付ける情報（ログイン中だけ）

本文の末尾に区切り線を引いて付ける。**サーバーで確かめた値だけ**を書く（URL から来た値はそのまま信じない）。

| 項目 | 出どころ | 確かめ方 |
| --- | --- | --- |
| ユーザー id・メールアドレス | `getAuthUser()`（JWT） | ― |
| 店舗 | `?tenant=` | `createClient()`（RLS）で `tenants` を読み、見えたときだけ id と名前を書く。見えなければ書かない |
| 開いていた画面 | `?from=` | `/` で始まるパスだけ（`safeNext()` と同じ判定）。クエリは落とす（`/signup?email=` のように個人情報が載りうる。025 §3-2 と同じ） |
| エラー番号 | `?digest=` | 英数字だけ・長さの上限 |
| ブラウザ | `headers()` の `user-agent` | 長さの上限で切る |

- 未ログインで送ったときは「未ログイン」とだけ書く（`?tenant=` があっても読まない。見えないので）
- 返信の引用で相手に戻っても困らない値だけにする（本人の情報）。Stripe の Customer id・管理画面の URL・内部のメモは入れない

### 4.5 メール

| 項目 | 値 |
| --- | --- |
| `from` | `assift <noreply@assift.com>`（024 で検証済みの差出人。認証メールと同じ） |
| `to` | `CONTACT_INBOX`（本番は `support@assift.com`） |
| `reply_to` | 相手のアドレス（ログイン中はアカウントのもの） |
| `subject` | `[お問い合わせ] {種類}：{内容の先頭 30 文字}`。改行・制御文字は空白に置き換える。Missive のルール（§5）がこの頭で拾う |
| `text` | 内容 + 区切り線 + 自動で付ける情報 |
| `Idempotency-Key` | `contact/{requestId}`。`requestId` はフォームを開いたときにクライアントが作る uuid（`crypto.randomUUID()`）で、送信の連打・やり直しで二重に届かない（Resend は 24 時間、同じ鍵の再送を 1 通にする） |

- Gmail は差出人と件名でスレッドをまとめるので、件名に内容の先頭を入れて問い合わせごとに分ける
- Missive は差出人（`noreply@`）を連絡先として表示するはず。誰からかは件名と本文の先頭（「返信先: …」）で分かるようにする。**Missive で返信したときの宛先が Reply-To になるか**はトライアルで確かめる（§8）。ならなければ §9-7

### 4.6 迷惑な投稿の対策（未ログインのフォーム）

| 段 | 内容 | 失敗したとき |
| --- | --- | --- |
| 1. ハニーポット | 画面の外に置いた入力欄（`website`。`tabIndex={-1}`・`autoComplete="off"`・`aria-hidden`）。値が入っていればボット | **成功を返して送らない**（ボットに判定の手がかりを与えない） |
| 2. 時間 | フォームを開いてから 3 秒未満の送信はボット | 同上 |
| 3. 回数の制限 | **Vercel Firewall のレート制限**（`/contact` への POST を IP ごとに 10 分で 5 回など）。コードは書かない | Vercel が 429 を返す。Action は失敗の表示になる |
| 4. CAPTCHA（後で） | 1〜3 で止まらない投稿が目立ったら Cloudflare Turnstile を足す | ― |

- 3 は Pro の Firewall でレート制限のルールが使えるか、料金がかかるかを確かめる（§9-3）。使えなければ、回数を数える置き場（DB の表など）が要るので別に決める
- 4 を足すときは `challenges.cloudflare.com` を `script-src`（nonce の `next/script`）と `frame-src` などに足す（`csp.ts`・`csp.test.ts`・022 §3）
- ログイン中は 1〜2 を見ない（ログインが確認になる）。3 は掛かる

## 5. Missive の設定（手作業）

Missive の細かい仕様はトライアルで確かめる。受信は今の Google Workspace のまま（MX は触らない。024・026）。

1. Missive のトライアル（30 日）を始める。プランは Productive を想定（ルールと AI が使える。1 人なら Starter で足りるかも §9-1）
2. Google のアカウント `admin@sundbox.app`（`support@` と `info@` はこのエイリアス）をつなぐ
3. 送信元に `support@assift.com` を選べるようにする（Gmail の「他のアドレスからメールを送信」に既にある。Missive が取り込むか確かめる）
4. ルール: 宛先が `support@assift.com` / `info@assift.com` の会話に「assift」のラベルを付け、返信の送信元を `support@` にする。`sundbox.app` のほかのメールと分ける
5. iOS アプリを入れ、「assift」のラベルだけ通知する
6. よく使う返信を Missive の Responses（定型文）にする
7. AI の下書きを使うなら、自分の OpenAI の鍵をつなぐ（Missive のクレジットは 25% 上乗せ）。ポリシーへの影響は §6・§9-8

## 8. 確かめ方

- Vitest: スキーマ（日本語のエラー・上限）、件名の改行と制御文字の置き換え、`?from=` のクエリ落とし、`?digest=` の判定、ハニーポットと時間の判定、`contactHref`
- 開発: 送るとコンソールにメールの中身が出る。ログイン中は店舗の名前が付き、他人の店舗の id を `?tenant=` に入れても付かない
- プレビュー（`RESEND_API_KEY` と `CONTACT_INBOX` を自分のアドレスで入れる）: 届いたメールの差出人・Reply-To・件名・本文。同じフォームで 2 回押しても 1 通
- Missive: 届いた会話にラベルが付き、iOS アプリに通知が来て、返信が**相手のアドレスに** `support@` から届く
- CSP: `npm run build && npm run start` で `/contact` を開き、`securitypolicyviolation` が 0 件（022 §6）

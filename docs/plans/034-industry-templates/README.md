- 前提: 014（初期設定。§3.2「テンプレートは仮の値」・§3.4「業種は保存しない」・§7「実データで見直す」の申し送り）/
  021（v1 データ移行。v1 のスキーマと件数）/ 026（カットオーバー。10/30 予定）
- 状態: **プラン（2026-10-19）。§3 の集計を流して結果を受け取ってから、§5 のテンプレートと §2-5 の業種の一覧を決める**

## 1. 目的と完了条件

業種テンプレート（`lib/setup/templates.ts`）は、014 で v1 の実データを見ずに決めた仮の値になっている。
また業種は初期設定のステップ 2 で聞いているのに保存していないので、運用を始めてから「どの業種でどの勤務が使われているか」を追えない。

- [ ] v1 の実データを集計し（§3）、業種の一覧とテンプレートを決める（§5）
- [ ] 店舗に業種を保存する（§4）。初期設定で選んだ業種がそのまま入り、店舗情報の画面で直せる
- [ ] テンプレートを見直した値に差し替える。LP の初期設定の図（`SetupSteps.tsx`）も合わせる

## 2. 決定（2026-10-19）

1. **業種は店舗（`tenants`）に持たせる。ユーザーには持たせない。** テンプレートを当てる単位が店舗なので、
   1 人で介護と保育の店舗を持つ場合に集計が混ざらない。ユーザー単位が要れば `owner_id` から導ける（逆はできない）
2. **新しく聞く画面は作らない。** 初期設定のステップ 2 で選んだ業種を保存するだけにする。
   アカウント作成時に聞くと、直後の初期設定と合わせて 2 回聞くことになり、014 §3.4「初回に聞くのは必要最小限」にも反する
3. **既存の店舗（v1 から移した店舗・初期設定を終えた店舗）には聞きに行かない。** `industry` は null のまま。
   ログイン時に聞く画面を挟むと、移行直後の利用者の問い合わせが増える。答えても画面が何も変わらず、答える理由が無い。
   店舗情報の画面に任意の欄を置くだけにする。既存の店舗の傾向は §3 の集計（店舗名からの推定）で見る
4. **どの版のテンプレートを当てたかも残す**（`industry_template_version`）。テンプレートを差し替えたあとに、新旧の版を比べられるようにする
5. 業種の一覧は §3 の結果で決める（未決。§6-1）

### 3.2 何を見るか

対象は**使われている店舗**: 直近 1 年に 30 コマ以上のアサインがあり、在籍スタッフが 1 人以上いる店舗。運営（`@assift.com`）の店舗は除く。
業種は**店舗名のキーワードからの推定**（`cvs` / `beauty` / `leisure` / `medical` / `retail` / `care` / `nursery` / `hotel` / `food` / `logistics` / `office` / `security` / `unknown`）。
今の 5 業種より細かく分けてあり、結果を見て統合するか分けるかを決める（介護と医療・小売とコンビニを分けるか、美容・ホテルなどを足すか）。
「ネットカフェ」が飲食に、「ホームセンター」が介護に入らないように、キーワードは上から順に当てる。

| ファイル | 内容 | 決めるもの |
| --- | --- | --- |
| `q1_industries.csv` | 業種ごとの店舗数・直近 2 年に作られた数・在籍スタッフ数の中央値・作成周期 | 業種の一覧と並び。`unknown` の割合 |
| `q2_names_by_industry.csv` | 業種ごとの勤務の名前の上位 40（使っている店舗の割合・アサインの割合・一覧の何番目か・最多の色と説明） | テンプレートの行・並び・色 |
| `q3_descriptions.csv` | 上位の名前ごとの説明（時間）の内訳 | テンプレートの説明（時間） |
| `q4_counts.csv` | 1 店舗あたりの勤務の数（登録数 / 使っている数。働く日・お休み別の四分位） | テンプレートの行数 |
| `q5_pairs.csv` | ペア（夜勤 → 明け など）の組み合わせ | どの業種にペアを入れるか |
| `q6_multi_tenant.csv` | 複数の店舗を持つ人の、店舗数と業種の数 | §2-1 の裏付け |
| `q7_names_overall.csv` | 業種を問わない勤務の名前の上位 100（`unknown` の店舗での数つき） | 「その他」のテンプレート |
| `private_sample_names.csv` | 業種ごとに 30 件（`unknown` は 300 件）の店舗名 | 推定の当たり外れの確認（手元だけ） |

勤務の名前・説明は NFKC にそろえてから数える（半角カナ・全角英数の揺れをまとめる）。
「使われている勤務」は直近 1 年に 1 コマ以上アサインがあったものに限る（作っただけで使っていない勤務を数えない）。

### 3.3 データの扱い

- 共有するのは `q*.csv` だけ（集計値）。勤務の名前は 5 店舗以上、説明は 3 店舗以上、ペアは 3 店舗以上で使われたものだけを出す
- `private_sample_names.csv` は店舗名そのもの。手元で目で確かめるだけにし、Claude やリポジトリには渡さない。
  外れの傾向（「〇〇センター」が多いなど）だけを言葉で伝え、キーワードを直して流し直す
- CSV はコミットしない。結果はこのプランの §5 に要約して残す
- プライバシーポリシーの利用目的「サービスの改善」に含まれる（017）

### 3.4 確かめたこと

v1 と同じ列の小さな表（13 店舗・運営の店舗 1 件・半角カナの店名・ペア・自動アサインの一時 Task を含む）をローカルの Postgres 17 に作って流し、
全ファイルが出ること・運営の店舗が除かれること・「ネットカフェ」「ホームセンター」「ｶﾌｪ」が意図どおりに分類されることを確かめた。

## 4. 実装（§5 の結果を受けて詰める）

### 4.1 スキーマ

`tenants` に 2 列を足す（`declarative sync --name tenant_industry`）。

```sql
-- 初期設定で選んだ業種（034）。null = 未回答（v1 から移した店舗・業種を選ばずに保存した店舗）
industry                  text check (industry in (...)),
-- 初期設定で当てたテンプレートの版（lib/setup/templates.ts の TEMPLATE_VERSION）。店舗情報の画面で業種を直しても変えない
industry_template_version smallint,
```

- enum ではなく `text` + `check`。業種を足す・まとめるときに、制約の差し替えで済む（enum は値を消せない）
- 値の一覧は `INDUSTRIES` と手で合わせる（`gen types` は `text` を `string` で出すので、TS の型ではずれに気付けない）。
  pgTAP で「`INDUSTRIES` の各値が入る / 一覧に無い値は入らない」を確かめる
- RLS は `tenants` の既存のポリシーのまま（列を足すだけ）

### 4.2 保存

- 初期設定のステップ 2: `save_setup_patterns` に `p_industry text default null`・`p_template_version smallint default null` を足し、
  勤務と同じトランザクションで `tenants` に書く。「保存済みから戻した」画面（業種を選んでいない）は null を渡し、既存の値を消さない
  （`coalesce(p_industry, industry)`）
- 引数を足すと別の関数（オーバーロード）になるので、差分 migration で古い引数の関数を `drop` する。`gen types` で型を作り直す
- 初期設定を再開したときは、保存した業種を画面に戻す（いまは保存していないので「業種を選びなおす」の確認ダイアログで置き換えを聞いている。014 §4.2）
- 店舗情報（`settings/general`）に「業種」の `Select`（任意。未選択に戻せる）を足す。版は変えない

### 4.3 テスト

- `templates.test.ts`: 既存の検査（全行が `patternInputSchema` を通る・色が重ならない）を新しいテンプレートでも通す
- pgTAP: 業種の check、`save_setup_patterns` が業種を書く / null で既存の値を消さない

## 5. テンプレートの見直し（§3 の結果で埋める）

### 5.1 集計の結果（q1〜q5。2026-10-19 に受け取った）

対象は使われている店舗 4,544 件。

**業種の推定は 76%（3,462 件）が `unknown`。** 店舗名に業種の言葉を入れない店が多い（ブランド名・「本店」など）。
業種の**割合**は当てにならず、名前に業種が出やすい業種（クリニック・保育園）ほど多めに出ている。

お休みについて:

- **お休みの区分（`dayoff`）は半数以上の店舗で使われていない**（`pct_no_dayoff_used` が 39〜83%）。
  「休み」「休」「希望休」「有給」を**働く日（`workday`）で作っている店舗が、お休みで作っている店舗とほぼ同じ数ある**
  （unknown で「休み」が workday 431 / dayoff 468）
- 名前は「休み」「休」が多い（13〜14%・10〜11%）。**「公休」は 4.7%** と少ない。**「希望休」は workday と dayoff を合わせて約 13%** で、「有給」（約 11%）より多い
- 色は「休み」「希望休」「有給」とも赤（`#F44336`）が最多

ペアは介護でも 8% ほど（夜勤 → 明け）。明けは働く日で作っている店舗が多い（介護で 7 対 3）。
1 店舗で使っている働く日の勤務は中央値 5〜7（food・beauty が多め）。

### 5.2 案

**業種（7 つ）**

| key | ラベル | 変更 |
| --- | --- | --- |
| `food` | 飲食店 | そのまま |
| `retail` | 小売・販売 | 「コンビニ」を外す（6 店舗。夜勤の形を裏付けるデータが無い） |
| `care` | 介護・福祉 | 「医療」を分ける。病棟（夜勤あり）はこちらを選んでもらう |
| `clinic` | クリニック・歯科 | **新設**。医療の 305 店舗は午前・午後の形で、介護と違う |
| `nursery` | 保育・教育 | そのまま |
| `beauty` | 美容・サロン | **新設**（72 店舗。介護に近い数） |
| `other` | その他 | そのまま |

**お休み（全業種で共通）**: 「公休・有給」→ **「休み・希望休・有給」**。

| 名前 | 色 | 理由 |
| --- | --- | --- |

| 希望休 | 赤 `#F44336` | 有給より多い。スタッフの希望なので目立たせる。v1 の最多の色 |
| 有給 | 緑 `#4CAF50` | いまのまま |

### 5.3 範囲の外で見つかったこと

v1 から移した店舗では、「休み」などを働く日で作っている店舗が多い（§5.1）。v2 ではこの区分が出勤日数の集計（`lib/shifts/count.ts`）と
自動作成（`lib/assist/problem.ts`）に効くので、**移行した店舗では「休み」が出勤日として数えられ、自動作成でも働く日として扱われる**。
v1 でも同じ扱いだったので移行の不具合ではないが、自動作成を使い始めると目立つ。利用者のデータを勝手に書き換えず、
勤務の設定画面で気付ける形（お休みらしい名前なのに働く日になっている勤務に注意を出す）を別のプランで検討する。

## 6. 未決

1. **業種の一覧。** 案は §5.2 の 7 つ（クリニック・歯科と美容・サロンを足す）。ボタンが増えると選びにくくなるので、7 つを上限にする
4. **明けの区分。** いまのテンプレートは「お休み」。v1 では「働く日」で作る店舗が多く、夜勤（16 時間）を 2 日分の勤務と数える施設の数え方にも合う。
   働く日にすると、週の上限（既定 5）に明けも数えられる
2. **「その他」を選んだときに、業種を任意で書いてもらうか。** 今の 5 つで足りていない業種を見つける手段になる。
   §3 で `unknown` が多く、店舗名から業種を推定できなければ入れる
3. **v1 のチュートリアルに既定の勤務があったか。** あったなら、その名前が多く出るのは既定値の影響なので、割り引いて読む

# 013: スタッフ別の制約と「必須 / なるべく」

自動アサイン制約（006 の `settings/restrictions`、012 のエンジン）を、店舗全体の規則とスタッフ別の規則の両方を持てる形にする。
あわせて規則ごとの強さ（必須 / なるべく）と、新しい 3 種類（週の最低勤務日数・土日祝の上限・なるべく休みの曜日）を足す。
012 §7 で「次の段階」に回した「制約ごとの必須 / できれば」と「スタッフごとの最低勤務日数」を扱うマイルストーン。

デザイン案は Artifact「制約の置き場所モック」（案 C: データは 1 つ、入口は 2 つ）。本プランが扱うのは ①〜③ で、
④「AI の結果から保存」は結果画面の別プランで詰めている（§3.1）。

> 番号: 012 の冒頭注記で 013 = データ移行 / 014 = カットオーバーに繰り下げていたが、本プランを 013 とし、
> 移行・カットオーバーを 014 / 015 にさらに繰り下げる。AGENTS.md の「本番に初回 push（マイルストーン 013）」は本プランの実装時に 015 へ直す。

**状態: 実装済み（確認待ち。2026-09-28）。実装ログは §9。**

## 1. 目的と完了条件

### 目的

- 「川田さんは週 3 日以上」「長澤さんは金曜はなるべく休み」のような**人ごとの規則を設定として残せる**ようにする。
  いまは毎回「AI への指示」に書くしかなく、次の実行では消える
- 規則ごとに**必ず守るか / なるべく守るか**を選べるようにする。いまは restrictions 由来の制約がすべてハード（012 §3.9）
- 規則を 1 か所（制約ページ）で見渡せ、スタッフ別の規則はそのスタッフの編集画面からも見て足せるようにする

### 完了条件

- 制約ページが「店舗全体」と「スタッフ別（人ごと）」の 2 群で一覧でき、各行に強さの札（必須 / なるべく）が出る
- 制約の登録画面で、対象（店舗全体 / スタッフ）・種類（7 種）・内容・強さを 1 画面で選べる
- スタッフの編集画面に「この人の規則」の一覧と追加の導線があり、追加・編集のあとはスタッフの編集画面に戻る
- 自動アサインが、スタッフ別の規則はその人にだけ、なるべくの規則は目的関数のソフト項として効かせる
- 新しい 3 種類がエンジン（model / validate / reasons / levers）で動き、Vitest で固定されている
- 必須の下限（週の最低勤務日数）で解が無くなったときに、指示と同じ仕組みでソフトに落として解き直す
- 守れなかったなるべくの規則が `assist_runs.result` に残る（画面への出し方は結果画面の別プラン。§3.1）
- 既存の 4 種類・既存の店舗の行は、そのまま「店舗全体・必須」として従来どおり動く（012 の Vitest がすべて通る）
- テナント境界の pgTAP に `restrictions.staff_id` の他店舗参照（23503）が入っている

## 3. 事前に確認したい決定

### 3.1 ④「AI の結果から保存」との境界 — **決定: 本プランは `AssistPanel.tsx` を触らない**

結果画面は別プランが作り直している最中なので、同じファイルを両方で書き換えない。本プランは結果の **jsonb に足す（既定値つきで古い run も読める）**
ところまでとし、画面への出し方は結果画面のプランに渡す。

| モック ④ の要素 | 扱い | 理由 |
| --- | --- | --- |
| 結果をモーダルで出す | **採らない** | 012 §11 でパネル / シートに決めて実装済み |
| 「指示の解釈」を制約ページと同じ書き方（対象 · 内容 · 強さ）で見せる | **語彙だけ取り入れる**。表示は結果画面プラン | 新しい 3 種は指示の `min_workdays` / `limit_weekends` / `prefer_off` と 1:1 に対応させる（§3.3）。保存の変換が素直になる |
| 「店舗の制約として保存」ボタン | **結果画面プラン** | UI も Action も結果画面側。本プランは種類と列を「指示から写せる形」にしておく |
| 元の文を行に残す（`AI への指示から: 「…」`） | **結果画面プラン**（列ごと） | 書き手が保存ボタンしか無い列を先に作ると、書かれない列と表示の分岐だけが残る。本番 push（015）までは migration が `init_schema` 1 本なので、後から足すのは安い |
| 保存できない種類（同じ日 / 別の日）の 1 行 | **結果画面プラン** | 同上 |
| 条件にできなかった言葉を残す | 対応不要 | 012 で実装済み（解釈の `unsupported`） |
| 「必須」を守れないとき「なるべく」に落として作る | **本プラン** | エンジンの挙動（§3.5） |
| 守れなかった「なるべく」の報告 | **データは本プラン**、表示は結果画面プラン | `result.restrictionOutcomes` に残す（§5.6）。表示されるまでの間、なるべくの規則が破れても画面には出ない（申し送り §7） |
| 制約の一手から規則の編集画面へ飛ぶ | **データは本プラン**（`Lever.restrictionId`）、リンクの差し替えは結果画面プラン | スタッフ別の規則が増えると、一覧へ飛ぶだけでは探しにくい |

**決定（2026-09-28）: 表示は結果画面プランを待つ。** 本番の初回 push（015）まで利用者がいないので、画面に出ない期間の実害は無い
（開発中は DB で確かめられる）。いま仮の節を足しても、結果画面プランが指示・制約・一手の並べ方を決めれば作り直しになりやすい。
ただし結果画面プランが 015 より後にずれ込むなら、そのときは本プラン側で仮の表示を足す。

### 3.2 データは 1 テーブル。`staff_id` / `hard` / `wdays` を足す — **推奨**

案 C（データは 1 つ）どおり、スタッフ別の規則も `restrictions` に入れる。スタッフ用の別テーブルは作らない
（エンジン・一覧・一手が 2 系統になる）。

- `staff_id uuid null`（null = 店舗全体）。複合 FK `(staff_id, tenant_id) → staffs (id, tenant_id) on delete cascade`
- `hard boolean not null default true`（012 §3.9 が見込んでいた列名）。既存の行・v1 から移す行は必須のまま
- `wdays smallint[] null`（なるべく休みの曜日だけが使う）

### 3.3 新しい 3 種類と、指示（Directive）との対応 — **推奨**

| kind | 画面の名前 | 1 行の説明 | 対応する指示 | 強さ |
| --- | --- | --- | --- | --- |
| `min_work_week` | 週の最低勤務日数 | 週に 3日 以上は入れる | `min_workdays`（`scope: 'week'`） | 必須 / なるべく |
| `max_weekend_days` | 土日祝の上限 | 土日祝の勤務は1か月に 2日 まで | `limit_weekends` | 必須 / なるべく |
| `prefer_dayoff_wdays` | なるべく休みの曜日 | 水曜はなるべく休み | `prefer_off`（`wdays`） | **なるべくのみ** |

- **「土日」ではなく「土日祝」**（モックは「土日」）。指示の `limit_weekends` と公平性の項（012 §5.4）が土日祝で数えているので揃える。
  揃えないと ④ で指示から保存したときに意味がずれる
- 「月に」は店舗の表示期間（`tenants.shift_cycle`）で言い換える（1か月 / 半月 / 2週間 / 1週間）。自動アサインは表示期間を 1 回で解くので、
  上限もその期間で数える。表示期間を変えると上限の意味も変わる（説明文に書く）
- 週の最低勤務日数は、**期間に丸ごと入る週だけ**で数える（端の週は期間の外を動かせない。指示の `min_workdays` と同じ。012 §10.3）
- 日数はどれも 1..7（既存の `days` の CHECK をそのまま使う）。土日祝の上限を 8 以上にしたい店舗は、上限を付けない場合とほぼ同じ
- なるべく休みの曜日を「必須」にすると「勤務できる曜日」と同じ意味になり、置き場所が 2 つになる。**なるべく固定**にし、
  フォームには「必ず休みにするなら、スタッフの「勤務できる曜日」を外します」と書く（DB でも `check (kind <> 'prefer_dayoff_wdays' or not hard)`）
- 7 種すべて、店舗全体にもスタッフにも使える（モックの注記どおり。「佐藤さんだけ連勤 3 日まで」も書ける）

### 3.4 強さの既定 — **推奨: 必須。なるべく休みの曜日だけなるべく**

モックの注記どおり。種類を切り替えたとき、利用者がまだ強さを触っていなければ種類の既定に合わせる。
なるべくの重みは 1 違反あたり `20 × 3 = 60`（指示の「強さ 3」相当）で始め、`npm run assist:eval` で確かめる（§5.5）。

### 3.5 必須の下限で解が無くなったとき — **推奨: 指示と同じく、まとめてソフトに落として 1 回だけ解き直す**

上限の規則（週の上限・連勤・組み合わせ・土日祝の上限）は、必須でも解が無くならない（全部 0・不足 = 枠数が実行可能。012 §5.1）。
解が無くなりうるのは**下限**（週の最低勤務日数）だけで、これは「必ず」の指示と同じ性質なので、012 §3.9 の仕組みに乗せる:
infeasible なら、ハードな指示と**必須の下限の規則を一緒に**ソフト（強さ 5）へ落として 1 回だけ解き直し、守れなかったものを結果に残す。

モック ② の説明文「この規則だけ「なるべく」に落として」は、どの規則が原因かを個別に探すことになる（012 §3.9 で見送った探索）。
文言は「守ると作れないときは、なるべくとして扱い、結果に「守れなかった」と残します」にする。

ただし、**明らかに守れない下限**（`days > 週の最大勤務日数` / `days > 勤務できる曜日の数`）は最初からソフトとして扱う。
店舗全体の「週 3 日以上」に週 2 日上限の人が 1 人いるだけで、毎回すべての「必ず」の指示まで緩むのを避ける。
この場合はスタッフの画面・制約ページの行にも「週の最大勤務日数（2日）より多いため守れません」と出す（§4.1 / §4.3）。

### 3.6 スタッフの編集画面の「この人の規則」はフォームの外に置く — **推奨（モックから変える）**

モック ③ は「この人の規則」をフォームの中（保存ボタンの上）に置いている。フォームを編集してから「規則を追加」を押すと、
保存していない入力が遷移で消える。**フォームのすぐ下に別の Paper（「この人の規則」）として置く**。
「いつも守ること」（曜日・パターン・週の最大）はフォームの中の最後の節に寄せるので、上下に並んで 1 か所で読める点は保てる。

### 3.7 並べ替えは廃止 — **推奨**

モックの注記どおり。上下ボタンは処理に影響せず、2 群に分けると意味が薄い。`position` 列は残して**登録順**として使い
（`nextPosition()` のまま。v1 から移す行の順も保てる）、一覧・`reorderRestrictions`・`ReorderHint` と
`reorder_positions` のホワイトリストの `'restrictions'` を外す。

### 3.8 退職したスタッフの規則 — **推奨: 残す。一覧ではスタッフ別の末尾に「退職済み」で出す**

退職は取り消せる（006 §3.6）ので消さない。自動アサインは在籍スタッフだけを読むので効かない（`normalizeRestrictions` が
在籍でない `staffId` を捨てる）。スタッフの削除では FK の cascade で消えるので、削除の確認文に「規則」を足す。

### 4.2 ② 制約の登録 / 編集（`settings/restrictions/new`・`[restrictionId]`）

種別選択カードの別画面（`?kind=` 無し）をやめ、**1 画面**にする（モック ②）。

```
制約の登録
┌─────────────────────────────────────────────┐
│ 対象      ○ 店舗全体（全員）                             │
│           ● スタッフを選ぶ [川田 真里奈 ▾]               │
│ 種類      [組み合わせを拒否][パターンの週の上限][連続勤務の上限]
│           [土日のどちらかは休み][週の最低勤務日数]        │
│           [土日祝の上限][なるべく休みの曜日]              │
│ 内容      週に [3] 日以上は入れる                         │
│ 強さ      [必須 | なるべく]                               │
│           守れないときは破り、結果に「守れなかった」と残します。
│                                        [キャンセル] [登録] │
└─────────────────────────────────────────────┘
```

- URL 状態は nuqs（`new/searchParams.ts`）: `?kind=`（種類）/ `?staffId=`（対象の初期値）/ `?from=staff`（戻り先）。
  カードを押すと `?kind=` を shallow で書き換える（Server の再描画は要らない。パターン・スタッフの選択肢は最初に渡す）
- 種類のカードは Mantine の `Radio.Card`（`SimpleGrid`）。出勤日のパターンが 0 件なら、パターンを使う種類を disabled（今の `KindSelector` と同じ）
- 対象のスタッフは在籍スタッフだけ（`Select`）。`?staffId=` が在籍でなければ未選択に落とす
- 強さは `SegmentedControl`。なるべく休みの曜日のときは出さず、§3.3 の 1 文を出す。説明文は強さに合わせて切り替える（§3.5 の文言）
- なるべく休みの曜日の内容は曜日の `Checkbox`（1〜6 個）
- 土日祝の上限の内容は「土日祝の勤務は{期間}に [n] 日まで」。{期間} は店舗の `shift_cycle` から
- 週の最低勤務日数でスタッフを選んでいて、`days` がその人の週の最大を超えるときは、内容の下に黄色の注意（§3.5）。保存は止めない
- **編集画面は種類を変えられない**（今と同じ。種類のカードは出さず、種類の名前を見出しに出す）。対象と強さと内容は変えられる
- 保存・削除のあとの戻り先: `?from=staff` かつ対象がスタッフなら、そのスタッフの編集画面。それ以外は制約ページ。
  戻り先の URL はサーバーが `staffId` から組む（入力から URL を受けない）
- キャンセルも同じ戻り先

## 5. 設計の要点

### 5.1 スキーマ

```sql
-- types.sql
create type public.restriction_kind as enum (
  'deny_pattern_pair', 'max_work_week', 'max_work_consecutive', 'sat_or_sun_dayoff',
  'min_work_week', 'max_weekend_days', 'prefer_dayoff_wdays'
);

-- tables/restrictions.sql（差分だけ）
create table public.restrictions (
  ...
  -- null = 店舗全体。スタッフを消すと規則も消える
  staff_id    uuid,
  -- 必須 = true。なるべく休みの曜日は常に false（勤務できる曜日と置き場所を分けない。013 §3.3）
  hard        boolean     not null default true,
  -- なるべく休みの曜日だけが使う（0 = 日曜）
  wdays       smallint[]  check (wdays is null or (cardinality(wdays) between 1 and 6 and wdays <@ array[0, 1, 2, 3, 4, 5, 6]::smallint[])),
  ...
  foreign key (staff_id, tenant_id) references public.staffs (id, tenant_id) on delete cascade,
  check (kind <> 'prefer_dayoff_wdays' or not hard)
);
create index restrictions_staff_id_idx on public.restrictions (staff_id);
```

### 9.2 プランから変えたこと

1. **明らかに守れない下限の判定は、正規化ではなく model で「スタッフ × 週」ごとに行う**（あわせて §9.5 の 2 で緩め方を 2 段にした）（§3.5 / §5.4 は正規化で行う書き方だった）。
   その週に勤務になりうる日（既存の勤務か、勤務になる変数がある日）の数と週の上限の小さいほうが `days` に届かなければ、その週だけソフト（強さ 5 相当）。
   正規化の段階では「その週にもう埋まっている日」や「枠の無い日」が分からず、店舗全体の週 3 日以上で 1 人の 1 週が足りないだけで
   `staticallyInfeasible` → すべての「必ず」が緩む、が残るため。画面の注意（`warnings.ts`）はプランどおり保存済みの値（週の上限・曜日の数）だけで出す
2. **結果の側のラベルは、土日祝の上限を「期間中」と書く**（`土日祝は期間中2日まで`）。設定画面は表示期間で言い換える（`1ヶ月に`）。
   エンジンは店舗の `shift_cycle` を受けていない。結果は 1 回の実行の話なので「期間中」で意味が通る。④ で指示から保存するときの文言は結果画面プランで揃える
3. **HEAD の型エラーを直した**: `applyAssistLever` が `relaxRestriction` に `index` を渡し、`restrictionsForLever` は `restrictionIndex` を読んでいた
   （`npm run typecheck` が 012 のコミット時点で落ちる）。実行時は `undefined` からラベルで引き直すので動いていた。名前を `restrictionIndex` に揃え、`restrictionId` も渡す
